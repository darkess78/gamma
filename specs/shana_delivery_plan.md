Date: 2026-10-23, America/Denver.  
Status, 2026-10-27: P1 through P5 have completed isolated technical verification. Human listening acceptance remains deferred. The owner authorized implementation and verification of the remaining phases and temporary activation for testing, with an easy dashboard. [Current P6-P9 work](shana_remaining_phases.md) records scope, decisions and evidence as they develop. No public stream launch, paid provider use or training is authorized by that test scope. The [P5 evidence](shana_private_interaction.md) retains the measured latency and conversational limits.

## Read this first

The goal is one continuing Shana who can share everyday life, do useful work,
play, stream, and develop through experience. Her judgment and expression should
fit the situation while her identity, relationships, commitments, and history
continue across activities and replaceable components.

The recommended route remains **a fresh coordination core with selective reuse**.
Finish and prove its first complete experience before expanding it. Keep the
production repairs, useful integrations, data, and bounded executors. Replace
competing decision owners as their capabilities join the new core. Neither a
wholesale rewrite nor activating the older modular checkout is justified.

The destination includes character development and learned ability. Prompted
traits, remembered facts, successful exercises, and trained behavior provide
different evidence. This plan gives each a place and a test. It cannot guarantee
that any chosen model will produce exactly the intended personality or that
subjective continuity can be proved by persistence tests.

| Stage | What becomes possible | Depends on |
| --- | --- | --- |
| P0 | A reliable starting inventory, requirement record, and change boundary | Current source and preserved evidence |
| P1 | Private text, quiet practice, conversation, switching, sleep, and recovery work as one experience | P0 |
| P2 | Useful memory, relationships, personal state, and unfinished intentions survive daily use and replacement | P1 |
| P3 | Shana owns useful practical tasks through verified results while remaining available | P1; P2 for durable context |
| P4 | Experience produces testable, revisable changes in interests, judgment, character, and skill | P2; real activities from P1/P3 |
| P5 | Natural private voice, Discord, and hideable desktop presence express the same Shana | P1-P2; shared resource and output contracts |
| H | One explicit live handover, after the channels needed for that release are ready | P1-P2 and release-specific capability gates |
| P6 | Screen-aware companionship and bounded shared play, followed by demonstrated game learning | P2/P4; observation and action adapters |
| P7 | Co-hosting grows into sustained independent streaming within an agreed broad plan | P4-P6 as needed by the stream format |
| P8 | Phone access and considerate proactive contact extend the same identity and commitments | P2-P3; authenticated channel and notification controls |
| P9 | Long-term operation, recovery, model replacement, and simplification remain dependable | Starts in P0; repeated at every release |

P3 and P4 can develop in small alternating slices. Voice need not wait for a
general training system. Stream hosting need not wait for autonomous gameplay
if the agreed stream format does not require it. A new capability does not get
its own independent personality, planner, or memory authority.

The [requirement map](shana_requirements_and_acceptance.md) lists the destination,
the present gaps, and the evidence needed to accept each part. Use it to check
coverage without rereading the whole plan.

## Shared design to carry through every stage

| Responsibility | Owner and boundary |
| --- | --- |
| Situation, attention, intentions, commitments, accepted personal changes, next decision | One Shana coordination owner. Mood, relationships, reflection, and interests inform it. |
| Work execution | Bounded capabilities and workers. They retain execution checkpoints and return evidence; they do not independently set Shana's priorities or activate themselves. |
| Inference | Replaceable model/provider adapters under existing resource admission. Specialist models earn their use through measured benefit. |
| Scheduling | Ordinary code watches events, results, deadlines, and bounded reconsideration conditions. The model chooses meaningful actions or waits; unchanged conditions do not cause an endless thinking loop. |
| Authorization, privacy, limits, cancellation, schema validation | Explicit code checks at action admission and effect commit. A model's confidence or opinion does not grant permission. |
| Speech and presentation | Shared approved output contract and target-specific consumers. Text, speech, subtitles, avatar state, and delivery confirmation remain distinct. |
| Durable state | Extend existing SQLite/journal/person mechanisms where practical. Use explicit ownership, atomic updates and durable references. Avoid building a general event platform or second parallel personal database without a demonstrated need. |

A capability contract should identify its authorized scope, inputs, run and
operation IDs, owner generation, deadline and resource budget, supported controls,
progress/checkpoint, result evidence, and uncertain effects. Acknowledged work,
executed work, verified result, and delivered communication are different states.
Retries preserve consumed limits. Unknown external effects require reconciliation,
not automatic replay or a promise of exactly-once network delivery.

Use a small shared activity lifecycle: proposed, accepted/ready, running, waiting,
pause requested/paused, completed, failed, or cancelled as needed. Preserve why
an activity exists, who requested it, its next unfinished step, and what would
justify revisiting it. Ordinary conversation can change attention without
necessarily stopping a worker. Add fields only when a real path needs them.

Keep lifecycle, situation, and execution state separate: awake/asleep/shutdown;
private work/stream/shared play; and queued/loading/generating/checking/playing
audio. Hiding an avatar is presentation. It does not implicitly sleep Shana.

## P1. Finish the first coherent private experience

This is the immediate work. Do not expand into games, phone control, model
training, or general repository authority to hide an incomplete first milestone.

### Necessary repairs and connections

1. **Use the actual current situation.** Resolve the scheduled-review session
   mismatch: the core reads `monitor-private`, while Monitor defaults to
   `monitor-local-stream`. Associate relevant conversation, activity and
   availability context explicitly, retaining audience boundaries. A hard-coded
   private session must not silently omit the current conversation.
2. **Permit quiet work during focus.** Separate the user's availability for
   interruption from permission and resource eligibility for background work.
   The present `relaxed` gate blocks all model-initiated practice during focus.
   Focus may suppress chatter while still allowing authorized quiet practice.
3. **Connect conversational activity control.** Add the smallest validated
   decisions needed to accept a bounded user task, ask to finish nonurgent work,
   switch when instructed, preserve the old activity, and later resume it. Current
   model actions are only wait, practice and report status; operator buttons do
   not establish natural conversational switching or commitment ownership.
4. **Ground ordinary progress answers.** Bind the requested activity to current
   artifacts and receipts before generating an explanation. Separate current
   success from older failures. If verification is absent or inconclusive, report
   that state. Do not rely on a magic exact status phrase to make an answer true.
5. **Make waiting lead somewhere.** Review on relevant changes or bounded due
   conditions. Back off when nothing changed. Explain expired permission or
   budget state; a wait that outlasts a finite permit must not appear to promise
   work afterward. Demonstrate both a sensible wait and an actual permitted
   self-start when the model judges it useful, without forcing a scripted choice.
6. **Keep deployment contained.** Shared Monitor changes must not select private
   routes on the ordinary host before those routes exist. Check normal and
   isolated factories separately. Review shared persona changes as part of the
   eventual release, even though the new core factory is currently unactivated.

### Connected acceptance journey

Use the selected private Monitor entry path, isolated data, and a real bounded
exercise on Gamma PC. Retain the run ID, artifacts, controls, actual process
identities, timings, and outcomes throughout this one journey:

1. Establish availability and a finite quiet-work permission through the real
   interaction. Shana chooses appropriate quiet work; a separate case shows
   that waiting is also a valid choice.
2. Chat normally while the worker runs. Ask about progress in ordinary language.
   Give a nonurgent request, then explicitly ask her to switch. Observe the
   preserved candidate and acknowledged pause or safe continuation boundary.
3. Restart the isolated process at a chosen saved boundary. Reconnect to a
   surviving worker or restore the same run, candidate, stage, and consumed
   limits. Resume the next unfinished step rather than regenerate a saved edit.
4. Put Shana to sleep while already authorized work remains. Workers can finish
   within existing instructions; new decisions wait. Wake her, reconcile actual
   results once, and verify her report against artifacts and independent checks.
5. Deliver duplicate/stale results and old-generation responses. They must not
   duplicate work, change personal state, publish, or replenish budgets.

Include useful failure cases: no progress, unavailable capability, expired scope,
changed checks, damaged checkpoint, and an uncertain in-flight inference. Fault
injection supports the journey; it does not substitute for a real process exit
and reopen. Existing HTTP and JavaScript contract tests remain useful, but they
are not visual or human interaction evidence.

Exit when the complete journey works through the chosen entry points and the
user can assess whether conversation, independence, and interruption feel
coherent. Resolve the specific gaps rather than adding more disconnected demos.

## P2. Make continuity useful in daily life

### Work

- Reconcile the candidate journal with production memory, person/account links,
  emotion history, working checkpoints and manual edits. Define one writer per
  kind of accepted personal state. Preserve stable IDs, attribution, audience,
  uncertainty, corrections and original experiences during a copied-data rehearsal.
- Add useful recall of conversations, authorized observations, decisions and
  commitments without requiring an explicit save request each time. Distinguish
  search/archive records, relevant current context, and accepted personal changes.
  Measure retrieval quality before adding embeddings or changing databases.
- Represent temporary mood, durable preferences, relationship-specific comfort,
  and pending learning hypotheses distinctly. Mood carries across tasks and can
  settle with elapsed time or experience; it does not weaken task reliability.
- Support corrections and direct personality editing. Keep an administrative edit
  record separate from an experience Shana remembers. Do not invent a remembered
  conversation to explain an edit the user has not told her about.
- Reconcile person links from established evidence, not display-name guesses.
  Allow callbacks from shared history appropriate to the audience. Opinion of a
  person, relationship familiarity and access permission remain separate.
- Extend sleep into a shared lifecycle: queue decisions and communications,
  let authorized workers continue, record maintenance proposals, and assemble
  completed/failed/waiting/changed-situation catch-up. User/system waking only
  initially. No fabricated first-person experience of work done while asleep.

Start with configurable retention for text and compact source references. Raw
continuous audio/video retention is an explicit later choice. Consolidation may
summarize and propose connections; material belief or personality changes must
pass the same acceptance process used while awake. Sleep is not a bypass.

### Acceptance

Across separate sessions and a restart, recover an unfinished goal, an earlier
decision, a partial recollection, and a correction with honest provenance. Reject
an incorrect account link and prevent private facts or private task details from
appearing in public context, including diagnostics and progress announcements.
Show relationship-specific familiarity without forced affection. Show mood
continuity without reduced accuracy or missed commitments.

Run a copied-state migration and reversal rehearsal. Preserve every post-migration
experience or explicitly retain it in a compatible journal; an old database
snapshot alone is not an acceptable operational rollback. Begin a small familiar
situation set for model/voice continuity comparisons now, before any replacement.

## P3. Give her useful, accountable work

Coding has high priority because it can support other improvements. Begin with
one disposable, useful task whose outcome can be observed. For example, a small
local tool with an actual user flow and a new request that changes the result.
Choose the example with the user when this stage starts; it is not an additional
feature requirement. Fixed exercises remain practice, not proof of general skill.

### Work

1. Connect bounded research, file/artifact work and repository coding to the
   shared activity contract. Reuse executor checks, protected tests, progress,
   candidate isolation and recovery. Broaden tool scope only as a task requires.
2. Let Shana clarify the goal when necessary, research, break down work, delegate
   specialist execution, inspect results, test the intended feature, repair ordinary
   failures, and return a concrete result. Research during brainstorming can
   inform the discussion; implementation needs a clear start under the current
   agreed boundary. Do not infer authority from an interesting idea alone.
3. Separate candidate preparation from promotion. The installed repository worker
   can apply source and restart services after checks; replace that authority
   before exposing it through the new core. Preparing and testing an improvement
   does not grant authority to affect running Shana.
4. Preserve conversation and truthful status while work runs. Escalate when a
   real decision, permission boundary, repeated unproductive failure or missing
   capability requires help. Routine reversible steps within the task proceed
   without repeated questions. Abandoning user work requires discussion.
5. Reuse resource routing and backend admission. Measure same-task cold/warm load,
   queue delay, first text, full text, voice start, cancellation and task progress.
   Compare with and without background work under matched conditions. Admission
   priority cannot preempt an already running nonpreemptive generation.

Run heavy inference, training and repository execution on Gamma PC. Protect the
user's working PC resources. Keep local and approved routed providers possible,
with data-scope, cost, endpoint, tool and concurrency limits. Ordinary code handles
placement, budgets and permissions. A smaller model may help a narrow decision;
it must demonstrate preserved judgment and character before serving dialogue.
Do not select new model sizes or add another manager model without evidence.

### Acceptance

Complete an unfamiliar bounded task through the actual artifact or running user
flow; a passing generated unit test alone is insufficient. Show one ordinary
repair, one useful blocker, conversation during work, and truthful progress.
Show that no source reaches running Shana, no external submission occurs, and no
paid service is used merely because a worker suggested it. Compare responsiveness
with the matched baseline and get user acceptance of the observed interaction.

## P4. Turn experience into growth that can be examined

Start evidence collection in P1, relationship and preference context in P2, and
small growth trials as soon as there are meaningful activities. Do not postpone
personality until all integrations exist. Also do not equate a new personality
note with learned character or make training a prerequisite for useful Shana.

### One learning path, with distinct kinds of change

| Step | Record or action | Acceptance evidence |
| --- | --- | --- |
| Experience | Compact situation, available options, action, expected outcome, observed outcome, source and uncertainty | Actual artifact, environment result, explicit correction or appropriately scoped observation |
| Interpretation | A tentative explanation or lesson, its scope, alternatives and supporting/contradicting evidence | Reviewable hypothesis; model agreement alone does not establish truth |
| Reversible trial | A narrow change to a decision policy, preference or skill guidance, with version and expiry/review condition | Better behavior on separate comparable situations without unacceptable regressions |
| Accepted development | Retain the useful change and its reasons; continue looking for contradictory outcomes | Behavior generalizes sufficiently for its scope and remains recognizable to the user |
| Training candidate, if justified | A specific component, curated dataset, frozen evaluation and recoverable model/adapter version | Improvement over incumbent on untouched evaluation plus character, privacy and capability regression checks |

Memory changes what information is available. Guidance or a policy changes how a
decision is made. Training changes model parameters; a decision policy can itself
be a trained model. Choose the component that explains the observed gap. Replacing
SQLite with weights would not solve provenance, correction or current commitments.
Training the main personality model on sparse daily conversation is not an early
default: overfitting, feedback bias and abrupt drift are concrete concerns here.

### Interests, character and relationships

Offer a small set of authorized, genuinely different opportunities and allow
exploration, silence, continuation, pause and return. Record outcomes and later
choices. Evidence of a developing interest includes unprompted revisits, specific
and revisable judgments, and choices that carry into unfamiliar contexts.
Writing that she likes something and then prompting her to choose it is circular.
Some seeded interests are fine, provided they are labeled as starting context.

Compare behavior with model and instructions held comparable where possible.
Distinguish changing opportunity, task difficulty, fatigue/resource limits, a
temporary mood and a lasting preference. Her own explanation can help form a
hypothesis; it does not certify boredom or an internal feeling. Do not force a
numeric boredom meter or fixed personality reward score.

She can drop her own projects, preserve paused work for later, and discuss
abandoning user commitments. Repeated abandonment is a pattern to investigate.
Develop warmth, playfulness and opinions through particular relationships while
preserving the ability to disagree. Do not optimize her toward pleasing one
person or copying the loudest public users. Learning from many people can include
questioning or rejecting what they do.

### Detecting wrong lessons and proving improvement

Use explicit corrections, missed commitments, real failures, regressions, sampled
apparent successes and occasional targeted questions. Silence, laughter, praise,
an LLM judge score and second-model agreement are weak or scoped signals. Separate
observation from causal interpretation. Retain contradictory cases and examine
whether a lesson was too broad, stale, incorrectly attributed or simply wrong.

Promotion depends on evidence quality, scope, generalization, contradiction,
reversibility and consequence. There is no universal number of repetitions or
confidence threshold that makes a lesson true. Keep narrow changes reversible;
undo the interpretation without erasing the experience. Preserve prior trained
versions and evaluate forgetting and changes outside the intended skill.

Reuse the existing improvement and coding-evaluation machinery where it fits.
The memory-triage coursework can inform one narrow classifier; its historical
dataset is not permission to train on raw private conversations. Split related
sessions/people/tasks to prevent leakage. Keep withheld checks out of learner
feedback and training. No automatic main-model retraining or live promotion.

Exit through demonstrated examples of honest recall, a revised wrong lesson,
an interest that survives a later revisit, and a narrowly improved skill or
decision on new cases. Longer-term character development remains a longitudinal
acceptance question, not a claim made after one successful evening.

## P5. Make private interaction feel natural

The isolated technical implementation is verified in
[P5 private voice and presence](shana_private_interaction.md). The owner selected
completion of the technical package with listening acceptance deferred and
Discord disconnected. Current cold first-audio latency and wording limits are
recorded there. The acceptance below still defines the intended experience;
technical verification does not establish that subjective experience. Use Brave
for the later private review. Production activation remains a separate decision.

### Voice and Discord

- Route STT observations and Discord messages into the same situation, identity,
  activity and output contracts. Reuse local STT/TTS and existing Discord owner
  controls; replace independent priority decisions rather than build another brain.
- Infer address from ongoing conversation, optional name cues, direct messages,
  other speakers and current activity. Private use initially favors catching
  intended speech. Uncertain high-consequence requests need clarification. Audio
  emotion or speaker labels are observations with uncertainty, not authority.
- Support listening while she speaks, echo handling, barge-in, stale-output
  cancellation and bounded queueing. Track generation at release and consumer
  acknowledgment. Separate generated audio, attempted playback and confirmed
  delivery; only human listening can establish audible naturalness.
- Tune wording, timing, prosody and neutral as well as emotional delivery. Do not
  hard-code a cheerful performance or let background work monopolize the model.

### Desktop presence

Create a thin presentation client or adapt an existing one after a small fit
check. Subscribe to approved state and output. Support hide/minimize, placement,
mute, reconnect and clear availability without making the avatar a state owner.
Disable individual capabilities independently of sleep and full shutdown. Keep
the existing multi-PC processing/presentation split available.

### Acceptance

Listen to real exchanges with silence, overlapping speech, thinking aloud,
another person speaking, interruption, a name cue, a DM and a background task.
Measure missed intended turns, false replies, start delay, cancellation and
actual stale playback. Test realistic room/noise conditions and degraded provider
availability. Have the user assess whether delivery fits the meaning and Shana.

In Discord, verify the selected recipient, owner controls, leaving/rejoining and
actual received text/audio in the authorized private test setting. Hide the
avatar while conversation/work continue, then sleep and confirm the different
effect. No public output is inferred from a private voice success.

## H. Hand over live ownership deliberately

Plan the required release channels in P0. The default recommendation is a useful
private release after P5, including whichever existing private entry paths the
user actually needs. If current Twitch use must continue, include its readiness
before handover. An earlier text-only release is possible only with an explicit
scope decision about temporarily inactive channels.

Until this gate, production is the sole live owner and the candidate uses isolated
state and outputs. Do not run two Shanas with access to the same private records,
work dispatch or live outputs and call that a gradual migration.

1. **Prepare a concrete release.** Pin source and models, audit the diff, preserve
   unrelated dirty work, rehearse on copied state, record authentication and route
   requirements without exposing credentials, and prove backups can be restored.
   Prepare the exact affected services and expected user-visible behavior.
2. **Cover all effect paths.** Fence personal writes, work dispatch and output
   publication at commit with the active owner/generation. Delegate or stop old
   selectors in stream, voice, Presence/proactive and coding paths. Channels not
   included are inactive, never left under an independent old controller.
3. **Reconcile in-flight work.** Admit no new old-owner work. Retain authorized
   workers and their evidence where compatible. Resolve unknown effects without
   replay. Retire or invalidate old queued speech, callbacks and stale decisions.
4. **Rehearse failure and reversal.** Crash during authority transfer, delay an
   old response, duplicate a worker result and lose a consumer connection. Verify
   that only the active generation can commit. Reverse authority using compatible
   current state and retain post-cutover experiences and unfinished work.
5. **Present the release for the user's activation decision.** Include tested
   behavior, known limitations, backup/rollback receipts, affected channels and
   required sign-in/client changes. Only after approval perform the bounded
   cutover, restart affected processes to load new code, and verify actual HTTP
   routes and permitted end-to-end user paths.

Retain the Shana API on 8000 and Dashboard on 8001, their route ownership, and
public HTTPS URL concepts. Follow the deployment reference. Do not silently
edit ignored machine-local files. Network or local configuration changes need
their own explicit scope in the proposed release. Keep a working recovery path
even when the new version has accepted fresh experiences.

The historical rejected Monitor/performer consumer probe remains excluded. Do
not rerun it under another name or tool. Any later delivery acceptance must have
its own permitted, specific scope and must not bypass that existing restriction.

Subsequent capabilities can be connected to the same active owner after their

## P6. Observe and participate in shared activities

Separate three deliverables: seeing a useful event, responding appropriately,
and acting competently. Screen access does not establish understanding, and
understanding does not grant control.

1. Start with owner-enabled, bounded observation of a selected application or
   game. Preserve source time, freshness, uncertainty and privacy. Test known
   screen changes, ambiguous views and stale feeds. Existing OSRS recognition
   recognizes limited screen states; it does not prove understanding of a drop,
   death, strategy or shared goal. Verify old UI defects before planning their fix.
2. Connect meaningful observations to the shared situation. Privately she reacts,
   jokes, remembers goals and occasionally suggests an idea, while allowing
   silence. Test both a quiet grinding session and a focused or exciting moment.
3. Add one bounded game action set in a private test environment. Minecraft's
   narrow protocol is a sensible reuse candidate, not an already capable player.
   Confirm the first game with the user. Preserve stop, loss-of-connection safety,
   deadlines, authorization and real environment result checks.
4. Develop one real skill through practice, outcome feedback and new situations.
   Compare performance against its own baseline on withheld scenarios. Track
   improving mechanics, reduced repeated mistakes, shared-goal recall and
   distinctive revisable tactics. Later broaden mechanics and games only after
   the observation/action loop works.

Exit with actual companionship during play, a bounded action with observed
consequences, and improvement on unfamiliar variants. Do not infer game learning
from a remembered mistake, scripted follow command, or model-generated strategy.

## P7. Grow from co-hosting to independent streams

Reuse Twitch inputs, moderation/review, performer outputs and pacing safeguards.
Move initiative and priorities into the shared owner. Stream context gives a
standing invitation to contribute, while focused moments still change judgment.
Private task contents, address/IP, relationship details and diagnostics remain
audience-scoped even while private work and public conversation coexist.

| Step | Experience | Evidence before expanding |
| --- | --- | --- |
| Private rehearsal | Follow an agreed broad idea, react to chat/events, choose useful contributions and quiet moments | Representative replay plus authorized private real adapters, no public release inferred |
| Supervised co-host | Fill most lulls, make callbacks, originate playful ideas, respect focused moments | User review of real sessions, actual received outputs, moderation and privacy checks |
| Owner briefly away | Carry chat and the current activity for a few minutes without requiring an owner decision for every turn | Bounded absence test, coherent return/catch-up, safe fallback on missing capabilities |
| Longer independent hosting | Sustain activities and interaction within the agreed broad plan, including quiet chat periods | Increasing session lengths, resource/reconnect endurance and user-assessed quality |
| Full intended session | Eventually sustain roughly four hours within the chosen format | An actual full session with meaningful participation, bounded resource use, incident evidence and owner stop control |

Avoid treating a four-hour uptime counter or constant speech as success. Review
whether contributions fit, interests provide direction, jokes and relationships
carry forward, privacy holds, and failures recover. Independent selection of a
whole stream concept is a later authority increase, not a prerequisite for hosting
inside a jointly chosen broad plan. Public launch is a separate user decision.

## P8. Extend the same Shana to the phone

Start with the smallest useful secure path: reaching her, getting an ongoing
task's result, and receiving a considered reminder. Select platform and client
approach after confirming the user's phone and actual desired operations. A DM
or browser client may satisfy part of the need; broader phone actions may need
an OS-specific app. Do not choose a native implementation just from a demo.

Carry the same person, commitments, availability, sleep state and conversation
history across desktop, Discord and phone. Add authenticated reconnection,
idempotent sends, delivery/acknowledgment state and offline handling. Do not copy
the main brain or private database into an independently deciding phone agent.

Shana can choose to share something or remind the user within granted contact
authority. Consider activity and recent contact; allow quiet periods and user
control. Acknowledgment ends that reminder exchange while preserving the
underlying unfinished commitment. A lost acknowledgment is not permission to
send repeatedly. More consequential phone actions require defined authority.

Acceptance: move a conversation between devices without duplicating a commitment;
ask about desktop work; receive a useful reminder at an appropriate moment;
acknowledge it and observe no nagging; lose and regain connectivity; sleep and
catch up consistently. Verify that notifications themselves do not reveal private
content on unintended surfaces. Broader phone assistance gets task-specific gates.

## P9. Keep the system maintainable as she develops

This work starts now and continues at each release:

- Keep one current requirement map, a short decision history and evidence-backed
  release records. Mark superseded choices. Simplify or remove an old controller
  only after its responsibilities and data have moved and regression proof exists.
  Review model calls: retain models for semantic judgment or specialized inference
  where they demonstrate benefit, and use ordinary code for reliable mechanics.
- Protect foreground responsiveness with measured limits on background work,
  batching/backoff, storage quotas and observable queues. Measure disk/model
  capacity on Gamma before expansion or training. A full disk, missing model,
  network outage or restart must yield an honest recoverable state.
- Maintain private encrypted/appropriately protected backups, restore rehearsals,
  compatible state migrations, source/config references and rollback versions.
  Choose concrete backup storage, retention and access during release preparation;
  this document does not create them or authorize uploads.
- Compare replacement models/voices on familiar histories and unfamiliar tasks.
  Check identity facts, evolving preferences, relationships, humor, disagreement,
  warmth, task quality, latency and skill retention. Reject replacements that are
  faster yet fail the needed character or ability. Skills in weights may require
  separate transfer; no universal interchangeability promise.
- Use longer everyday sessions and sampled cases to detect regression. Allow
  understandable development, rather than freeze Shana against every historical
  response. Keep a practical correction path without making the user label all
  interactions or manually approve every ordinary personal preference.

## Verification and release evidence

Each implementation packet names its requested outcome, source baseline, allowed
files/state, capability authority, resource limits, acceptance cases and excluded
actions. Prefer scoped coding-workers jobs under the current worker guide, local
Qwen by default, one active job per provider and at most five independent jobs
globally. Keep packets inside the verified context limit. Codex reviews source
hashes, `proposal.diff`, `result.json`, and actual behavior before integration.
This planning task did not dispatch implementation workers.

Windows CLI launchers and all nested children run hidden using a non-console
launcher and `CREATE_NO_WINDOW`, with durable logs. Verify the paths actually
used, not only a wrapper unit test. Gamma PC owns runtime execution and heavy
compute. Preserve the original Windows, production and older-candidate trees.

Use narrow meaningful tests, then broaden according to touched contracts. Check
JavaScript syntax for changed modules and `git diff --check`. Exercise real entry
paths and artifacts for claims about integration. Keep raw private captures local
and bounded; sanitized release receipts can summarize evidence without publishing
memory or credentials. No new tests or inference were required to write this plan.

| Evidence | Required record |
| --- | --- |
| Feature result | Entry point, expected outcome, actual artifact/received behavior, versions and limitations |
| Behavioral judgment | Situation/history, observed choice and outcome, user feedback where subjective, counterexamples |
| Performance | Comparable conditions, samples and distributions, queue/load/generation breakdown; no cold/warm sleight of hand |
| Recovery | Actual interruption point, preserved IDs/artifacts/limits, resumed step and unresolved effects |
| Activation | Exact release source, backups, authority transition, affected channels/services, user decision and post-cutover checks |

Acceptance means the intended behavior works, relevant checks pass or remaining
issues are explicitly resolved for release, and the user has assessed the parts
that depend on feel. Test counts, model self-reports and worker completion alone
do not establish that outcome.

## Tracking without losing the direction

Keep this document for sequencing and the requirement map for coverage. Trello
should remain a readable summary: short outcome title, current decision, next
observable step, and link to evidence. Do not turn every behavioral example into
a new controller or a giant card. Update the board only when requested/authorized.

After each slice, record: what changed for the user, what was actually observed,
what remains unproved, and the next smallest work item that advances the same
experience. If a requirement changes, retain the old decision and reason. If
evidence disproves a design, revise the design rather than defend sunk work.

The first execution packet should be **P1**, beginning with current-context and
focus eligibility, then shared conversational activity control and grounded
reporting, and ending with the connected recovery journey. Later packets follow
the dependencies above. Calendar and cost estimates should follow these bounded
packets and measured spikes; the research-heavy stages cannot honestly be assigned
fixed completion dates from the present evidence.
